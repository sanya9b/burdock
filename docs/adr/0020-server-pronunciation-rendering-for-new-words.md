# 0020. Серверний модуль Pronunciation: вимова для нових слів рендериться на сервері один раз і кешується

| Поле | Значення |
|---|---|
| Статус | Proposed (напрям власника 01.10.2026: «починай синтезувати звуки і потім зробимо модуль на сервері для синтезування нових слів, які будуть додаватись користувачем чи адміном») |
| Дата | 2026-10-01 |
| Рішення журналу | T7 (у редакції ADR 0019), Q17 (одна VM, Docker Compose), Q37 |
| Специфікації | 08 (стадія `audio render`), 09 (новий модуль, маніфест активів), 10 (нічого персонального в кліпах), 14 (контейнер `kokoro` у compose) |
| Уточнює | ADR 0019 (пре-рендер у пайплайні лишається для словника; цей ADR додає шлях для слів, яких у пайплайні не було) |

## Контекст

ADR 0019 закріпив пре-рендер вимови під час збирання контенту: 01.10.2026 усі 9 792 слова словника відрендерено у чотирьох голосах Kokoro-82M (≈ 39 тисяч кліпів, ≈ 11 ядро-годин, ≈ 250 МБ). Це покриває слова, які відомі наперед. Але власник хоче, щоб нові слова теж отримували вимову автоматично: слова, які додає адміністратор (власні списки `content/own-lists/`, правки після рецензії, нові голоси), і в майбутньому слова, які додає сам користувач.

Онлайн-синтез у момент натискання кнопки на телефоні відкинуто (обговорення 01.10.2026): застосунок працює офлайн, віджети не ходять на сервер, перше прослуховування з очікуванням 1–3 с зіпсує момент «слово дня», а синтез на єдиній VM конкурує за процесор з API. Натомість потрібен сервер, який рендерить кліп **один раз** після появи слова і далі віддає його як звичайний незмінний актив.

## Варіанти

1. Нічого не додавати: адмін запускає `audio render` вручну на своїй машині при кожній зміні контенту й завантажує файли у сховище. Безкоштовно, але слова користувачів так не обслужити, і кожна правка потребує ручного кроку.
2. **Серверний модуль Pronunciation із сайдкаром Kokoro**: API приймає запит на вимову, фоновий воркер рендерить відсутні кліпи через локальний контейнер Kokoro і кладе їх в об'єктне сховище; клієнт отримує кліп за незмінною адресою, а доти користується системним TTS.
3. Хмарний TTS (Azure, Google) із сервера: не потребує CPU на VM, але це сторонній обробник, інша ліцензія на вихід і щомісячна плата; суперечить рішенню 0019 про власний рушій.
4. Нейромережа на пристрої: +20–80 МБ до застосунку й подвійна інтеграція (ADR 0019, варіант 3), відкинуто раніше.

## Рішення

Варіант 2.

1. **Модуль `pronunciation`** (`Burdock.Server.Modules.Pronunciation`, структура Domain / Application / Infrastructure / Endpoints, власна схема `pronunciation`). Таблиця `clip (lexeme_id, voice, text, engine, engine_version, model_sha256, status queued | rendered | failed, path, sha256, bytes, requested_by admin | pipeline | user, created_at, rendered_at, last_error)` з унікальністю `(lexeme_id, voice, engine_version)`; таблиця `voice` дублює каталог голосів добірки (id, назва, акцент, стать, зразок).
2. **Ендпоінти.** `GET /v1/pronunciation/voices` (публічний каталог); `GET /v1/pronunciation/clips/{lexemeId}/{voice}` → `302` на CDN-адресу готового кліпа, `202` якщо він у черзі, `404` якщо запиту не було (клієнт у двох останніх випадках озвучує системним TTS, як і зараз); `POST /v1/pronunciation/clips {lexemeId, text, voices?}` ставить у чергу відсутні кліпи й повертає стан кожного голосу; виклик ідемпотентний. У v1 запис дозволено лише адміністратору (ключ у заголовку `X-Burdock-Admin-Key`, значення із sops-секретів; переходить на OpenIddict-скоуп `content:write`, щойно з'явиться модуль Identity). Шлях для слів користувача додається окремим ADR разом із самою функцією «мої слова»: там потрібні квота на користувача, обмеження частоти й місце в privacy-переліку.
3. **Правила тексту** живуть у домені: `PronunciationText` приймає 1–64 символи латиницею з апострофом, дефісом, крапкою й пробілами (a.m., call into question), відкидає керівні символи, адреси й порожні рядки; `VoiceId` і каталог голосів беруться з `Burdock.Domain.Vocabulary` (ті самі чотири голоси, що в застосунку).
4. **Рендер.** Контейнер `kokoro` у тому самому Compose (образ із `content/pipeline/audio/`: Python, kokoro-onnx, ffmpeg з imageio-ffmpeg, FastAPI + uvicorn, усі MIT/BSD/Apache-2.0), доступний лише в приватній мережі Compose: `POST /render {text, voice, speed}` → `audio/mp4`. Той самий код і параметри, що в стадії `audio render` (темп 0,9, AAC-LC 32 кбіт/с, обрізання тиші), тому кліпи з пайплайну і з сервера не відрізняються. Порт `IPronunciationRenderer` в Application; адаптер `KokoroHttpRenderer`; одночасність рендеру обмежена одним-двома запитами, тайм-аут 30 с; невдачі повторюються через чергу завдань (спека 09 §3.12) із позначкою `failed` після трьох спроб.
5. **Сховище й доставка.** Порт `IClipStore`: у розробці локальна тека (`Pronunciation:StorePath`), у продакшні Hetzner Object Storage за Bunny CDN (спека 09 §3.4). Шлях незмінний і версіонований: `pronunciation/{engineVersion}/{voice}/{lexemeId}.m4a`, `Cache-Control: public, max-age=31536000, immutable`; зміна рушія чи голосу означає новий `engineVersion` і повторний рендер у фоні, а не перезапис.
6. **Зв'язок із пайплайном.** Пре-рендер (ADR 0019) лишається основним шляхом для словника: пайплайн завантажує готові кліпи й реєструє їх у `clip` зі статусом `rendered` і `requested_by = pipeline`. Серверний рендер потрібен лише для слів, яких у пайплайні не було.

## Наслідки

- Плюс: нове слово отримує вимову без участі людини й без змін у застосунку; один код рендеру для пайплайну й сервера; клієнт ніколи не чекає на синтез, бо має TTS-запасний шлях.
- Мінус: ще один контейнер (≈ 1 ГБ пам'яті, сплески CPU) на єдиній VM; на CX33 (4 vCPU, 8 ГБ) цього достатньо, але воркер має працювати з низьким пріоритетом і обмеженою одночасністю; Arm-плани не підходять для сайдкара (повільний onnxruntime).
- Безпека: запис лише з адміністративним ключем; текст обмежений доменними правилами; у кліпах і їхніх шляхах немає персональних даних, тому privacy-перелік (спека 10) не змінюється до появи слів користувача.
- Ліцензії: FastAPI (MIT) і uvicorn (BSD-3) додаються до контейнера `kokoro`; у .NET нових пакетів немає.
