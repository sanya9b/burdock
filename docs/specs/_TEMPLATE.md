# Шаблон специфікації напрямку

Кожна специфікація в `docs/specs/` дотримується цієї структури. Мова: українська. Ідентифікатори коду, назви пакетів, API та файлів: англійською.

```markdown
# NN. Назва напрямку

| Поле | Значення |
|---|---|
| Статус | Draft / Approved / Superseded |
| Версія | 0.1 |
| Дата | YYYY-MM-DD |
| Власник | Власник продукту / Архітектор |
| Джерела рішень | посилання на docs/decisions/*.md (номери Q/T) |
| Пов'язані специфікації | посилання |

## 0. Контекст для ШІ-агента
Короткий (10-20 рядків) промт: що це за напрямок, які документи прочитати перед роботою,
які правила не можна порушувати, де лежить код цього напрямку, як перевірити результат.

## 1. Мета й межі
Що входить у v1, що явно не входить, що відкладено (з посиланням на roadmap).

## 2. Вимоги
Функціональні (FR-NN-x) та нефункціональні (NFR-NN-x) вимоги з пріоритетами MoSCoW.

## 3. Проєктування
Моделі, діаграми (Mermaid), контракти, потоки, платформові обмеження.

## 4. Рішення та компроміси
Таблиця «варіант / плюси / мінуси / обрано і чому». Посилання на ADR.

## 5. Критерії приймання
Перевірювані твердження (Given/When/Then або чеклист), які закривають вимоги.

## 6. Ризики
Ризик, ймовірність, вплив, пом'якшення.

## 7. Відкриті питання
Що ще не вирішено, хто вирішує, до якої дати.

## 8. Джерела
Посилання на офіційну документацію, використану в цій специфікації.
```

## Правила написання

1. Джерело істини для рішень: `docs/decisions/2026-09-25-interview.md`. Специфікація не може змінювати рішення, лише деталізувати. Розбіжність оформлюється як ADR.
2. Факти про платформи, версії та ліцензії беруться з `docs/research/2026-09-25-research-brief.md` із посиланням. Твердження, позначені там як unverified/low, у специфікації не цитуються як факти.
3. Кожна вимога має ідентифікатор (`FR-04-3`), щоб на неї можна було послатися з коду, тесту чи задачі.
4. Терміни інтерфейсу пишуться так, як вони з'являться користувачу (наприклад «Серія», «Колючки», «Реп'яшок»), і зібрані у `docs/glossary.md`.
5. Діаграми: Mermaid у Markdown. Макети екранів: текстові wireframe-описи плюс HTML-прев'ю в `design/preview/`.
6. Числа, що є політикою (ліміти, інтервали, ціни), виносяться в таблицю констант із назвою параметра конфігурації, щоб їх можна було змінити без правки логіки.
7. Не описувати те, що очевидно з коду. Описувати наміри, обмеження, інваріанти, компроміси.
