# Контракт API «Реп’яха»

`openapi.v1.json` — опублікований контракт API v1 (`https://api.burdock.org`). Файл генерується з коду сервера (`Microsoft.AspNetCore.OpenApi`, трансформери в `src/server/Burdock.Server.Api/OpenApiContract.cs`) і комітиться в репозиторій (спека 09 FR-09-25, спека 16 FR-16-11).

## Як оновити

Знімок знімається з живого хоста контрактним тестом `tests/Burdock.Server.ContractTests` (піднімає PostgreSQL 18 через Testcontainers, потрібен Docker):

```
BURDOCK_UPDATE_SNAPSHOTS=1 dotnet test --project tests/Burdock.Server.ContractTests
```

Без змінної середовища той самий тест падає, якщо документ, який віддає сервер, відрізняється від файла. Так CI (`ci-server`, `dotnet test --solution Burdock.Server.slnx`) блокує зміну контракту без оновленого знімка.

Чому не на етапі збірки: `Microsoft.Extensions.ApiDescription.Server` запускає хост під час `dotnet build`, а хост на старті виконує hosted-сервіси з доступом до бази (сидер клієнта OpenIddict, міграції). Знімок із тесту відповідає документу, який віддає справжній хост, і не потребує бази на машині збірки.

## Правила змін

- Додавання ендпоінта, поля відповіді чи необов’язкового поля запиту: звичайний PR зі зміненим знімком.
- Ламка зміна (видалення чи перейменування поля, зміна типу, нова обов’язкова властивість запиту, зміна коду помилки): ADR і нова версія маршруту (`/v2/...`), стара версія живе паралельно до кінця підтримки (спека 09 §3.1).
- Ендпоінт `POST /v1/connect/token` навмисно не описаний: його форма задана OAuth 2.0 і OpenIddict (спека 09 §3.3.1).
- Автоматична перевірка ламких змін (`oasdiff breaking` проти `main`, спека 14) додається до `ci-server` після вибору версії дії; до того diff знімка переглядається в PR вручну.

## Клієнти

Застосунок не генерує клієнт із цього документа: він використовує ті самі DTO з `src/shared/Burdock.Contracts` і типізований шлюз `HttpSyncGateway` (чернетка ADR 0021 пояснює відхилення від Kiota зі спеки 09 §3.2). Для зовнішніх споживачів документ є єдиним джерелом.
